# Phase 0 — Risk Register และ Assumptions

## Risk Register

| ID | ความเสี่ยง | ผลกระทบ | โอกาสเกิด | แนวทางจัดการที่เสนอ |
|---|---|---|---|---|
| **R-01** | **ชื่อโครงการ ("LIFE IT Smart Service Center") กับระบบเดิมจริง ("ISMS Governance System") ไม่ตรงขอบเขตกัน** — ระบบเดิมมี 12 โมดูล GRC/ISMS/PDPA (Data Classification, Legal Compliance, Privacy/PDPA, Risk, AI/Cloud Register, Awareness, Audit Evidence/Management, Governance Documents, PDF Designer, Operations Hardening, Integration Outbox, Action Permission) ที่ไม่อยู่ในรายการโมดูลเป้าหมายของคำสั่งเริ่มต้น | สูงมาก — ถ้าตัดออกโดยไม่ตั้งใจ กองทุนฯ จะเสียความสามารถ ISMS/PDPA compliance ที่ใช้งานจริงอยู่ | สูง (เกิดแน่ถ้าไม่ยืนยัน) | ยึดกฎ "ห้ามตัดฟังก์ชันเดิมโดยไม่ได้รับอนุญาต" — รวมโมดูลกลุ่ม E ไว้ในขอบเขต Migration ทั้งหมดเป็นค่าเริ่มต้น (ดู Assumption A-01) เว้นแต่ผู้ใช้จะสั่งตัดออกเป็นลายลักษณ์อักษร |
| **R-02** | RBAC เดิมมี 5 บทบาทตายตัว (`User/Approver/ITAdmin/Executive/DPO`) และ **1 ผู้ใช้ = 1 บทบาทเดียว** (ไม่ใช่ many-to-many) ต่างจากสเปกใหม่ที่ต้องการ Configurable RBAC 9 บทบาทเริ่มต้นและ many-to-many | กลาง-สูง — ต้องออกแบบ mapping บทบาทและอาจกระทบสิทธิ์ผู้ใช้ที่มีอยู่ 27 คนตอน cutover | สูง | Phase 3 ต้อง mapping 5 role เดิม → role ใหม่ชัดเจนก่อน (เช่น ITAdmin→it_admin, Executive→executive/manager, DPO→dpo, Approver→approver, User→user) และให้ IT Admin ยืนยันสิทธิ์รายคนก่อน Go-live ไม่ auto-map แบบเดา |
| **R-03** | Google Sheets ไม่มี Foreign Key จริง — ความสัมพันธ์ข้าม Sheet (เช่น `AssetID`, `VendorID`, `CatalogID`) ตรวจด้วยโค้ดเท่านั้น อาจมี orphaned reference สะสมจากการใช้งานจริงหลายปี | สูง — Import เข้า PostgreSQL ที่มี FK constraint จริงอาจ fail หรือถูกปฏิเสธเป็นจำนวนมาก | กลาง-สูง | เครื่องมือ Migration (Phase 7) ต้องมีขั้นตอน "ตรวจสอบ Foreign Key" และ "รายงานข้อมูลที่ขาด FK" ตามที่กำหนดไว้แล้วในคำสั่งข้อ 8 — รัน Dry Run ก่อนเสมอ |
| **R-04** | `Users.PasswordHash/PasswordSalt` เป็น hash เฉพาะของระบบเดิม **ไม่สามารถ migrate เข้า Supabase Auth ได้โดยตรง** | สูง — ผู้ใช้ 27 คน login ไม่ได้ทันทีถ้าไม่วางแผน | แน่นอน (ทราบล่วงหน้า) | ใช้ flow "Admin เชิญผู้ใช้ตั้งรหัสผ่านใหม่ผ่านอีเมล" ตามที่สเปกกำหนดไว้แล้ว (ปิด Public Sign-up) วางแผนสื่อสารกับผู้ใช้ 27 คนล่วงหน้าก่อน Cutover |
| **R-05** | Field Designer (custom field/table designer) และ PDF/Document Designer (Word-like editor ลากวาง) เป็นฟีเจอร์ที่ซับซ้อนมากเทียบกับ ROI ในระบบใหม่ — ใช้เวลาพัฒนาสูง | กลาง — เสี่ยงทำให้ Timeline ยืดหากพยายามย้าย 1:1 | กลาง | เสนอเลื่อนสองโมดูลนี้ไปหลัง Go-live (Phase 9 เป็นต้นไป) หรือแทนที่ด้วยเครื่องมือสำเร็จรูป (เช่น export เป็น PDF ผ่าน headless browser/React print stylesheet) — ต้องขอการตัดสินใจจากผู้ใช้ก่อนเริ่ม Phase 4 |
| **R-06** | ไม่มีตาราง `Departments`/`Positions` ที่ normalize แล้ว — เป็น free-text กระจายในหลาย Sheet คาดว่ามีชื่อหน่วยงานสะกดต่างกัน | กลาง — กระทบคุณภาพ Master Data และ RLS ตามหน่วยงานในระบบใหม่ | สูง (ข้อมูล free-text มักไม่สม่ำเสมอ) | Phase 7 (Data Migration) ต้องมีขั้นตอน "ตรวจสอบข้อมูลซ้ำ/ทำความสะอาด" ของ Department ก่อนสร้างตาราง `departments` แล้วให้ IT Admin ยืนยันรายชื่อหน่วยงานที่ถูกต้องก่อน Import |
| **R-07** | ไม่มีตาราง `Contracts` แยก — ข้อมูลสัญญากระจายอยู่ใน `VendorRegister`, `ConfigurationItems.ContractRef`, `MaintenancePlans.ContractNo` | กลาง | กลาง | Phase 2 ต้องออกแบบตาราง `contracts` ใหม่ทั้งหมดแล้วเขียนสคริปต์ consolidate จาก 3 แหล่งข้อมูลเดิม ไม่ใช่การย้ายแบบ 1:1 |
| **R-08** | เอกสาร `docs/02_โครงสร้างฐานข้อมูล.md` (Data Dictionary เดิม) **ล้าสมัย** — ขาดไป 22 จาก 93 ทะเบียนจริงใน `Config.gs > DB_SCHEMA` | สูง — ถ้าใช้เอกสารนี้เป็นแหล่งเดียวใน Phase 2 จะออกแบบ Schema ใหม่ไม่ครบ | เกิดแล้ว (พบใน Phase 0 นี้) | **บันทึกไว้แล้ว**: Phase 2 ต้องอ่าน `Config.gs > DB_SCHEMA` โดยตรงเป็นหลัก ใช้ `docs/02` เป็นข้อมูลอ้างอิงประกอบเท่านั้น (ดู `phase0-data_dictionary_reference.md`) |
| **R-09** | ตาม `docs/18_PRODUCTION_ROLLOUT_v1.11.md` ระบบเดิมยังมี Acceptance ค้าง: authenticated UAT รายบทบาท, fault-injection/retry/retention UAT, sandbox rollback drill **ยังไม่เสร็จ** บน Production จริง | กลาง — อาจมี defect ที่ยังไม่ถูกพบในโมดูล Workflow/Attachment/Integration (เพิ่มใหม่ v1.11) ซึ่งจะถูกย้ายไปเป็นต้นแบบระบบใหม่ | กลาง | ระหว่างออกแบบ Phase 4/6 ให้ตรวจสอบ business logic ของ 3 โมดูลนี้อย่างละเอียดจาก Source Code จริง ไม่ใช่จากเอกสารอย่างเดียว และเพิ่ม Test Case เฉพาะจุดที่ `docs/18` ระบุว่ายังไม่ผ่าน UAT |
| **R-10** | Phase 0 นี้ไม่มีสิทธิ์เข้าถึง Production Google Sheets/Spreadsheet จริง (มีแต่ Source Code) — ไม่ทราบจำนวนแถวจริง คุณภาพข้อมูลจริง หรือปัญหาข้อมูลซ้ำ/เสียหายที่มีอยู่จริง | กลาง-สูง — Phase 7 อาจเจอปัญหาข้อมูลที่คาดไม่ถึง | สูง | Phase 7 ต้องเริ่มด้วย Export + Dry Run + Reconciliation Report ตามที่กำหนดไว้แล้ว ก่อนเชื่อว่าข้อมูล "พร้อม Import" |
| **R-11** | LINE Login (OAuth/PKCE) และ LINE Messaging API เป็น dependency ภายนอกที่ผูกกับ LINE Developers Console/LINE OA config ซึ่งเก็บเป็น Script Properties (**ไม่อยู่ใน Source Code ที่ตรวจได้**) | สูง — ถ้าไม่ได้ค่า Channel ID/Secret/Token จากเจ้าของระบบ จะ implement LINE Login ในระบบใหม่ไม่ได้เลย | แน่นอน (เป็นข้อมูลลับที่ตั้งใจไม่เก็บใน Source) | ต้องขอค่า Script Properties ที่เกี่ยวกับ LINE จากเจ้าของระบบโดยตรงตอนเริ่ม Phase 3 (Auth) ผ่านช่องทางปลอดภัย ไม่ใช่ทาง chat — บันทึกเป็น TODO ที่อนุญาตได้ตามกฎข้อ 15.6 |
| **R-12** | ไฟล์แนบมี 2 เส้นทางคู่ขนาน (Drive.gs เดิม แบบ direct link vs Attachment Registry ใหม่ v1.11) — Ticket แบบ Anonymous/Public/LINE เดิมบางส่วนยังใช้ path เดิม | กลาง | กลาง | เครื่องมือ Migration ไฟล์ (ข้อ 8) ต้องรองรับทั้งสอง path แยกกัน — Mapping metadata คนละแบบ |
| **R-13** | PDF generation (Evidence Export, PDF Designer, รายงาน Ticket/Asset) พึ่งพา Google Docs API ปัจจุบัน — สถาปัตยกรรมเป้าหมาย (Cloudflare Workers) ยังไม่ได้กำหนดเครื่องมือสร้าง PDF ทดแทน | กลาง | สูง (ต้องตัดสินใจแน่ ๆ ใน Phase 4) | ต้องเลือกแนวทาง (เช่น headless Chromium service, PDF library ที่รันบน Workers ได้, หรือ Supabase Edge Function) ก่อนเริ่มพัฒนาโมดูล Report/Evidence — ยังไม่ตัดสินใจใน Phase 0 นี้ |
| **R-14** | SLA คำนวณตามเวลาทำการ/วันหยุด (Business-hours SLA) มี logic เฉพาะฝังใน `Module_OperationsHardening.gs` + ค่า `SLA_*` ใน Settings — ถ้าย้ายไม่ครบจะทำให้ตัวเลข SLA ผิดทันทีที่ Go-live | สูง (กระทบความน่าเชื่อถือของรายงาน SLA ทันที) | กลาง | Phase 4/6 ต้องอ่าน `Module_OperationsHardening.gs` แบบละเอียด (ยังไม่ได้อ่านลึกใน Phase 0 นี้) ก่อน implement SLA engine ใหม่ และทำ Test Case เทียบผลลัพธ์กับระบบเดิมแบบขนาน (parallel run) ก่อนเชื่อถือ |
| **R-15** | Repo ปัจจุบันมีโฟลเดอร์ `.git` แต่ **ไม่มี git history จริง** (ตรวจแล้วว่า `git status`/`git log` รายงาน "not a git repository") | ต่ำ-กลาง | แน่นอน (ตรวจพบแล้ว) | Phase 1 ต้อง `git init` ใหม่ (หรือยืนยันกับผู้ใช้ก่อน) แล้วตั้งค่า remote GitHub ก่อนสร้าง Monorepo — ไม่ใช่ปัญหาของ Phase 0 แต่ต้องรู้ก่อนเริ่ม Phase 1 |
| **R-16** | ระบบใหม่ต้องรองรับ 27 concurrent users แต่ Phase 0 นี้ไม่มีข้อมูล baseline ประสิทธิภาพจริงของระบบเดิม (Login/Dashboard/Ticket list/รายงาน) ตามที่คำสั่งข้อ 10 ต้องการวัดและรายงาน | ต่ำ-กลาง | กลาง | ต้องวัด Baseline จากระบบเดิมจริง (ผ่าน `scripts/live-browser-check.mjs` หรือเครื่องมือ manual) ก่อนอ้างว่าระบบใหม่ "เร็วกว่า" — เสนอทำในช่วงต้น Phase 8 (Testing) ไม่ใช่ Phase 0 |

## Assumptions (สมมติฐานที่ตั้งไว้เพราะข้อมูลไม่ครบ — ตามกฎข้อ 18)

| ID | สมมติฐาน | เหตุผล |
|---|---|---|
| **A-01** | ขอบเขต Migration ทั้งหมดครอบคลุม **43 โมดูล** ที่ตรวจพบจริง (รวมกลุ่ม E ทั้ง 12 โมดูล GRC/ISMS/PDPA) ไม่ใช่แค่ 26 โมดูลในรายการเป้าหมายเดิมของคำสั่ง | ป้องกันการตัดฟังก์ชันเดิมโดยไม่ได้รับอนุญาตตามกฎข้อ 4/16 — เป็นสมมติฐานที่ปลอดภัยกว่าการตัดออก |
| **A-02** | "ผู้ใช้งานภายในองค์กรประมาณ 27 คน" หมายถึงจำนวนบัญชีที่ Active ใน `Users` sheet รวมทุกบทบาท (ไม่รวมผู้แจ้งภายนอกผ่าน LINE/Public ซึ่งไม่จำกัดจำนวน) | คำสั่งเริ่มต้นไม่ได้ระบุ peak concurrency ที่แน่ชัด ใช้ตัวเลขนี้เป็น baseline การทดสอบ Phase 8 |
| **A-03** | LINE ยังคงเป็นช่องทางแจ้งเตือนหลักในระบบใหม่ (ไม่เปลี่ยนไปใช้อีเมลเป็นหลัก) เพราะเป็นการตัดสินใจทางธุรกิจที่ชัดเจนในระบบเดิม (เห็นจาก `Notification.gs` และ CHANGELOG หลายรุ่น) | เป็นพฤติกรรมเดิมที่ผู้ใช้คุ้นเคยแล้ว การเปลี่ยนช่องทางแจ้งเตือนโดยไม่ขอคือการตัดฟังก์ชันเดิมโดยปริยาย |
| **A-04** | เครื่องมือสร้าง PDF/รายงานในระบบใหม่ยังไม่กำหนดในสถาปัตยกรรมเป้าหมาย จะตัดสินใจใน Phase 4 หลังสำรวจตัวเลือกที่ใช้ได้ฟรี/ต้นทุนต่ำบน Cloudflare Workers | คำสั่งเริ่มต้นไม่ได้ระบุเครื่องมือ PDF ไว้ใน Technology Stack |
| **A-05** | เอกสารเดิม `docs/01`–`docs/18` ถือว่าถูกต้องเป็นส่วนใหญ่ ยกเว้นจุดที่ตรวจพบว่าไม่ตรงกับ Source Code จริงและได้บันทึกไว้แล้ว (เช่น R-08 กรณี `docs/02`) | เอกสารเดิมมีคุณภาพสูงและอัปเดตต่อเนื่องทุก release แต่ Source Code ต้องเป็นแหล่งอ้างอิงสุดท้ายเสมอเมื่อขัดแย้งกัน |
| **A-06** | Phase 0 นี้วิเคราะห์จาก Source Code ในเครื่องเท่านั้น **ไม่ได้เชื่อมต่อ Google Sheets/Drive Production จริง** — ตัวเลขจำนวนแถวข้อมูลจริง คุณภาพข้อมูลจริง ยังไม่ทราบจนกว่าจะถึง Phase 7 | ไม่มีการให้สิทธิ์เข้าถึง Production ในขั้นตอนนี้ และ Phase 0 ห้ามแก้ไข/เชื่อมต่อระบบเดิมอยู่แล้วตามกฎข้อ 20 |
| **A-07** | ค่า Secret ทั้งหมด (LINE Channel ID/Secret, Script Properties อื่น ๆ) จะขอจากเจ้าของระบบโดยตรงเมื่อถึง Phase ที่ต้องใช้จริง (Phase 3 เป็นต้นไป) ไม่ใช่ตอนนี้ | สอดคล้องกับกฎข้อ 6/12 ห้ามใส่ Secret จริงในโค้ดหรือเอกสาร และห้ามเว้น TODO ยกเว้นกรณี Secret |
| **A-08** | Google Apps Script quota/behavior (เช่น `LockService` serialize การเขียนทุก Sheet) เป็นสาเหตุหลักที่ทำให้ระบบเดิม "โหลดช้า" ตามที่ผู้ใช้ระบุในบริบทโครงการ — PostgreSQL + Connection Pooling จะแก้ปัญหานี้โดยธรรมชาติ | ยังไม่มีข้อมูล Performance Baseline จริง (ดู R-16) จึงเป็นสมมติฐานเชิงเทคนิคที่ต้องยืนยันด้วยการวัดจริงใน Phase 8 |

## คำถามที่ควรยืนยันกับเจ้าของระบบก่อนเริ่ม Phase 1 (มีผลต่อโครงสร้าง — ตามกฎข้อ 19)

1. **ยืนยันขอบเขต:** ต้องการย้ายโมดูลกลุ่ม E (GRC/ISMS/PDPA — 12 โมดูล) ทั้งหมดไปด้วยหรือไม่ หรือต้องการเฉพาะ ITSM
   (กลุ่ม A–D) ก่อนแล้วค่อยทำกลุ่ม E ในเฟสถัดไป — **มีผลโดยตรงต่อจำนวน Phase 6 และขนาดของ Database Schema**
2. **ยืนยันบทบาท:** จะ mapping 5 บทบาทเดิม (User/Approver/ITAdmin/Executive/DPO) เข้ากับ 9 บทบาทเป้าหมายอย่างไร
   (เช่น ต้องการแยก `super_admin` ออกจาก `it_admin` จริงหรือไม่ ต้องการเพิ่ม `technician`/`manager`/`auditor` ตั้งแต่
   Cutover วันแรกหรือไม่) — **มีผลต่อ RLS Policy และ Permission Matrix ทั้งระบบ**
3. **Field Designer / PDF Designer:** ต้องการย้าย 1:1 หรือยอมรับให้ตัด/เลื่อนไปทำหลัง Go-live (ดู R-05)
